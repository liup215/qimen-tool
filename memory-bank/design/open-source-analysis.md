# 开源命理/奇门项目分析

> 分析对象：mingli-skills、Numerologist_skills、oceanjustinlin/qimen
> 目的：借鉴其工程化思路，优化当前 `qimen-tool` 的设计与实现

---

## 1. mingli-skills — AI 命理工程化

### 1.1 项目定位

- 专为 Claude Code / LLM Agent 设计的工程化命理 Skill 系统。
- 包含紫微斗数、八字、六爻、印占、奇门遁甲五大体系，总计约 114 个文件。
- 核心理念：**LLM 做推理解读，确定性计算交给脚本，每个结论可追溯、可验证。**

### 1.2 核心特点

| 特点 | 说明 |
|------|------|
| **多阶段 SOP + Gate Check** | 每个体系拆解为多个 Phase，每步完成后做机械校验，不通过则补做 |
| **独立评估者（GAN 模式）** | 断卦完成后由 evaluator 独立复核，找出矛盾与遗漏 |
| **排盘引擎 + 144 项自检** | Python 排盘脚本 + verify.py，含格式层、逻辑层、一致性断言 |
| **断卦 9 步 SOP** | 盘外梳理 → 用神 → 盘外格局 → 大环境 → 值符值使 → 竖看 → 横看 → 综合 → 应期 |
| **知识库查表** | 用神表、格局、八门九星八神象意全部 JSON 化，不靠模型记忆 |
| **Trace 日志** | 每次断卦记录结构化 JSON，用于批量失败模式分析 |
| **pre-commit 回归验证** | 每次提交跑 50 盘随机验证 |

### 1.3 奇门模块文件结构

```
qimen-dunjia/
├── scripts/qimen.py          # 9 步排盘引擎
├── scripts/verify.py         # 144 项断言验证
├── scripts/trace.py          # trace 日志
├── scripts/analyze_traces.py # 失败模式分析
├── data/                     # 17 个 JSON 数据文件
│   ├── dipan_18ju.json       # 18 局地盘排布
│   ├── shigan_keying_81.json # 81 组十干克应
│   ├── duanjua_knowledge.json# 断卦知识库
│   ├── geju_xiangyi.json     # 30 种具名格局 + 象意
│   ├── jiugong_xiangyi.json  # 九宫象意
│   ├── sanqi_xiangyi.json    # 三奇专项
│   └── ...                   # 五行/空亡/击刑/入墓/门迫/马星等
├── research/                 # 12 份深度调研报告
├── ARCHITECTURE.md           # 三层架构说明
├── KNOWN_ISSUES.md           # 已知坑和防线
└── SKILL.md / duanjua-skill.md # 断卦 SOP
```

### 1.4 最值得借鉴的点

1. **144 项排盘自检**：不只是单元测试，而是覆盖格式、逻辑、一致性的断言链，失败时有决策树修复指南。
2. **9 步断卦 SOP**：系统化的解盘流程，特别是"一票否决"、"竖看 7 层"、"横看生克"、"应期三步法"。
3. **知识库查表驱动**：所有吉凶、格局、象意从 JSON 查，杜绝模型记忆错误。
4. **Trace 日志 + 失败模式分析**：把每次运行变成可迭代的数据资产。
5. **独立 evaluator**：用 LLM 做对抗性复核，不是自我评估。

## 2. Numerologist_skills — 给"赛博半仙"戴紧箍咒

### 2.1 项目定位

- 目标：减少 LLM 在排盘、流派口径、步骤顺序和解释链路上的幻觉。
- 把传统术数拆成可审计、可复用、可逐步扩展的工程模块。
- 当前包含奇门遁甲、紫微斗数、四柱八字。

### 2.2 核心特点

| 特点 | 说明 |
|------|------|
| **先追问，再输出** | 信息不全时优先补参数，不硬排盘 |
| **确定性计算外包** | 历法换算、固定排盘交给脚本 |
| **先声明口径，再做结论** | 默认规则集 `mainline-cn-v1`，流派、换日规则、闰月归属先说清楚 |
| **只给结构化参考** | 健康、法律、财务等高风险场景不替代现实专业建议 |
| **两段式访谈** | 第一轮 6 个核心问题 + 第二轮条件追问 |
| **不展示完整推理链** | 只展示关键依据和必要计算结果 |
| **默认规则集固定** | 时家转盘奇门、置闰法、中宫寄坤、北京时间默认时区 |

### 2.3 mainline-cn-v1 规则集要点

- 体系：时家转盘奇门
- 时区：默认 `Asia/Shanghai`，海外必须补城市/时区
- 定局：置闰法工程化实现
- 中宫：一律寄坤处理
- 值符值使：与值符同落时干所到之宫（不另做独立转门计算）
- 边界提醒：节气边界前后 24 小时内输出明确提醒

### 2.4 最值得借鉴的点

1. **规则集版本化**：明确 `mainline-cn-v1`，让用户知道用的是什么口径，便于后续升级。
2. **结构化访谈流程**：先确认"看什么、哪一刻、判断什么"，避免信息不足硬算。
3. **高风险主题免责声明**：疾病、法律、投资等必须附现实建议提醒。
4. **输出克制**：不堆术语、不展示完整推理链、先说人话再补术语。
5. **中宫寄坤规则明确**：转盘法常见但易出分歧，应写死规则。

## 3. oceanjustinlin/qimen — 奇门遁甲 · AI 决策引擎

### 3.1 项目定位

- Vue 全栈应用 + Cloudflare + Supabase + Gemini。
- 把古典"情境—时间—行动"框架用确定性规则引擎实现，再让 AI 负责表达。
- 同时提供八字、奇门两套 Agent Skill。

### 3.2 核心特点

| 特点 | 说明 |
|------|------|
| **规则引擎而非提示词** | 旺衰、格局、喜忌、用神由本地引擎计算，LLM 只做翻译 |
| **评分引擎量化** | 能量底板、结构强度、月令旺衰、门星神合力 |
| **天地盘干生克** | 每宫记录 `stem_relation`：天生地/地生天/天克地/地克天/比和 |
| **格局落宫索引** | `detected_patterns` 含 name/palace/detail/nature |
| **古籍命例校验** | `fixtures/classical-golden-cases/` 高置信经典命例 |
| **追问深挖机制** | 一局一解，正本不动，补丁只能引用盘面证据 |
| **双轴语义路由** | 先判断问题该用奇门（局势模型）还是八字（禀赋模型） |
| **流式输出 + 自愈重试** | 哨兵分段协议，结构校验失败自动非流式重试 |
| **可审计推演过程** | 每个结论可追溯到结构化数据 |

### 3.3 输出数据结构亮点

- `chart.door_index` / `chart.star_index`：门/星 → 宫反查字典，便于快速定位用神
- `chart.day_stem.palace`：日干落宫，直接代表求测者
- `chart.time_stem_visible`：时干明干，代表所问之事
- `chart.palaces[].stem_relation`：天地盘干五行关系
- `chart.palaces[].door_palace_relation`：门与宫关系，用于判断门迫
- `warnings`：边界提醒、寄宫提醒

### 3.4 最值得借鉴的点

1. **门/星反查索引**：极大简化用神定位逻辑。
2. **天地盘干关系字段**：让"十干克应"和"格局"判断有数据可依。
3. **格局落宫索引**：格局不再悬空，能指出影响哪个宫、哪个角色。
4. **评分引擎与旺衰修复**：`qimenProsperity` 按月令计算九星旺相休囚死。
5. **经典命例回归测试**：用古籍案例验证规则引擎准确率。
6. **追问机制设计**：一局一解、不覆盖原文、不引入新盘面元素。

## 4. 对当前 `qimen-tool` 的借鉴建议

### 4.1 短期可落地（MVP 增强）

| 借鉴点 | 当前状态 | 建议动作 |
|--------|---------|---------|
| **规则集版本化** | 未明确 | 在输出和文档中声明 `mainline-cn-v1`，明确转盘法、拆补法、中宫寄坤 |
| **排盘自检脚本** | 有单元测试 | 升级为类似 verify.py 的断言链，覆盖格式+逻辑+一致性 |
| **门/星反查索引** | 无 | 在 plate JSON 中增加 `door_index` / `star_index` / `god_index` |
| **天地盘干关系** | 无 | 每宫增加 `stem_relation` 字段 |
| **格局落宫索引** | 简单检测 | `detected_patterns` 增加 `palace` 和 `nature` |
| **中宫寄坤明确** | 已实现 | 在输出中明确标注寄坤处理 |
| **高风险免责声明** | 无 | 所有 `interpret` 输出末尾附加免责声明 |
| **应期规则** | 设计文档未涉及 | 在解释引擎设计文档中补充应期三步法 |

### 4.2 中期可扩展（解释引擎升级）

| 借鉴点 | 建议动作 |
|--------|---------|
| **9 步断卦 SOP** | 将当前 5 步流程扩展为：盘外梳理 → 用神 → 一票否决 → 大环境 → 值符值使 → 竖看 → 横看 → 综合 → 应期 |
| **一票否决机制** | 优先检查五不遇时、六仪击刑、三奇入墓、天网四张、全局伏吟反吟 |
| **竖看 7 层** | 每宫按：天地盘干 → 八门 → 九星 → 八神 → 四害 → 九宫象意 → 三奇 顺序分析 |
| **知识库扩展** | 扩展 `patterns.json` 为具名格局库；新增 `jiugong_xiangyi.json`、`sanqi_xiangyi.json` |
| **状态评分细化** | 参考 oceanjustinlin 的 `qimenProsperity`，按月令计算九星旺相休囚死 |
| **结构化访谈** | 若做交互式 skill，实现 Numerologist 的两段式访谈 |

### 4.3 长期可考虑

| 借鉴点 | 建议动作 |
|--------|---------|
| **独立 evaluator** | 在 skill 中增加 LLM 复核步骤，检查用神落宫、格局名称、生克方向、四害遗漏 |
| **Trace 日志系统** | 每次运行生成结构化 trace JSON，用于失败模式分析和版本迭代 |
| **经典案例回归** | 积累 `fixtures/classical-golden-cases/`，用权威盘例验证排盘和解释 |
| **追问深挖机制** | 支持在原盘基础上追问，不重新排盘、不覆盖原文 |
| **多体系联动** | 未来可与八字等术数做交叉验证（当前项目范围外） |

## 5. 关键结论

1. **确定性计算 + LLM 解读解耦** 是三家共同遵循的黄金法则。当前项目 Go CLI 的架构天然适合这条路线。
2. **规则集版本化和口径声明** 是减少争议、保证可复现的基础。
3. **系统化 SOP + 知识库查表** 比自由文本解释更可控、更可测试。
4. **排盘后的断言自检** 比单纯单元测试更能保证结果正确性。
5. **输出克制 + 免责声明** 是面向普通用户的必要约束。
6. **应期、具名格局、三奇专项、九宫象意** 是解释引擎从"能用"到"好用"的关键补齐项。
